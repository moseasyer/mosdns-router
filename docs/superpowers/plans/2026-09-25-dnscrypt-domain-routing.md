# DNSCrypt and Domain Routing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Route China-set domains through the dynamic DHCP plugin and every other domain through a loopback dnscrypt-proxy configured by default with authenticated Quad9 Secure DNSCrypt v2 stamps.

**Architecture:** `internal/dnscrypt` renders a deterministic `dnscrypt-proxy.toml`; `internal/rules` downloads and converts a pinned `v2fly/domain-list-community` snapshot; `internal/mosdnsconfig` renders the routing sequence. Integration tests run the custom MOSDNS binary against local DHCP and foreign DNS mocks and prove there is no fallback path.

**Tech Stack:** Go 1.25, YAML v3, dnscrypt-proxy 2.1.18 configuration format, MOSDNS v5.3.4, `miekg/dns`, local UDP/TCP DNS servers.

**Spec:** `docs/superpowers/specs/2026-09-25-mosdns-dnscrypt-cdn-ech-design.md`

## Global Constraints

- No generated domestic upstream may contain a Chinese public DNS address.
- Foreign user queries must enter `127.0.0.1:15353` over TCP and must never fall back to the DHCP plugin.
- The local DNSCrypt listener must serve TCP as well as UDP, because the foreign forward uses TCP.
- DNSCrypt configuration must use complete DNS stamps, not bare resolver IPs.
- Default DNSCrypt endpoints are Quad9 Secure DNSCrypt v2, IPv4, no ECS, with authenticated provider certificates.
- Plain bootstrap is used only for DNSCrypt provider-name resolution and must not receive ordinary user queries.
- DNS rules are pinned by source commit and SHA-256; failed downloads keep last-known-good.
- System services are not installed in this plan.
- TDD is mandatory; every task ends with a focused commit.

## Review Focus

- `server_names` must contain resolver names, while each `[static]` entry's `stamp` contains a complete stamp.
- `ignore_system_dns=true` and a non-53 loopback listener are mandatory to prevent bootstrap loops.
- A SERVFAIL from the foreign resolver must not trigger the domestic branch.
- Unsupported or cyclic `include:` entries in domain-rule data must fail without replacing the last valid list.
- The generated MOSDNS sequence must preserve DNSSEC/EDNS behavior apart from the later explicitly synthetic response paths.
- The `keyword:` validator is coupled to the pinned MOSDNS matcher: `KeywordMatcher.Add` normalises with `NormalizeDomain` (`ToLower` + `TrimDot`), so a keyword the normalisation would change is a rule the gateway matches on as something else. `keyword:a.` becomes `keyword:a` and matches every name containing the letter a. The guard therefore requires `NormalizeDomain(value) == value`, calling the pinned matcher rather than restating it, so a change to that normalisation reaches the guard instead of passing beside it.
- The China list is read at load time and is load-bearing in two different ways: a missing or unreadable file must stop `mosdns-router start` loudly, and a file that loads with no rules must not fail at all — it routes every name, China ones included, to the foreign branch in silence. The second is the only fail-open state in the design, and the end-to-end case for it is the one that proves the silence rather than the misroute alone.

`configs/cn-domains.txt` and `configs/source-lock.json` are the output of one real
`mosdns-cdnctl update-lists --pin-remote HEAD` run against the reviewed upstream
commit the lock records, and they are committed for review and so a fresh
installation ships a list whose source is known without any network access. They
are not generated by `MOSDNS_ROUTER_UPDATE` and not by the Makefile: that variable
drives the two document generators in `internal/config` and `internal/mosdnsconfig`
and nothing else. `internal/rules/committed_test.go` is what holds the committed
pair to the promise its lock makes, offline.

`plugin/executable/dhcp_forward/` is not in this File Map. It comes from the
foundation plan, and this plan only *configures* it: `mosdnsconfig.Render` writes
`state_file`, `cache_entries`, `upstream_port` and `failure_policy` into the
`dhcp_forward` plugin's arguments, and the plugin's own `upstream_port` and
`failure_policy` semantics (0 means 53, and `use-last-good` retains the last
generation that had upstreams) are that plan's contract, verified here from the
rendered document's side.

`cmd/mosdns-cdnctl/publish.go` is the document pair publication, kept separate from
`update_lists.go`'s list publication because the two are different jobs over
different files: the list pair is a digest-checked source lock beside a generated
list, published under the shared control lock, while the document pair is two
rendered configurations published to /etc with no lock. What they share is the
discipline, and the reason it is written twice is stated in the file: the machinery
in `internal/rules` is unexported and its rollback tests drive those internals by
name, so sharing it would mean reshaping a publisher those tests hold.

`configs/dnscrypt-proxy.toml` has no update route at all, and the two committed
list artifacts do not have a runtime one either — that asymmetry is worth stating
plainly. Nothing in this plan rewrites `configs/dnscrypt-proxy.toml` after Task 1:
there is no command for it, no `--check` that compares it against a remote, and no
timer that touches it. It is Quad9's published Secure DNSCrypt v2 IPv4 endpoints,
reviewed once, and `internal/dnscrypt/config_test.go` holds the committed file to
`Render(config.Defaults(), Defaults())` byte for byte. `configs/cn-domains.txt` and
`configs/source-lock.json`, by contrast, are published at runtime — by
`update-lists --pin-remote HEAD`, deliberately, and by nothing else.

So an operator who wants a different provider is outside what this plan built. The
two honest routes are to edit the *installed* `/etc/mosdns/dnscrypt-proxy.toml` and
restart dnscrypt-proxy, which `validate` will then report as a `rendered-mismatch`
(it is no longer what `dnscrypt.Defaults()` produces, which is the report doing its
job), or to change `Defaults()` in this repository and let the next package carry
the new stamps. A policy-driven stamp set needs a `foreign.stamps` field, a
validation rule for it, and a publish route that does not exist yet; none of that is
in this plan, and the resolver document `render` produces therefore always carries
the reviewed Quad9 set.

- [ ] **Step 6: Add explicit list-management commands**

Implement:

```text
mosdns-cdnctl update-lists --check
mosdns-cdnctl update-lists --pin-remote HEAD
```

`--check` downloads metadata into memory and reports whether the locked commit/archive differs without writing files. `--pin-remote` resolves the remote commit once, verifies and converts the archive, writes `source-lock.json` and `cn-domains.txt` atomically, and prints the accepted commit and digest. Neither mode may use the system resolver to fetch rule files.

`--check` reads the published pair **without** taking the shared control lock, and that is deliberate: holding the lock is what a pin does, and a pin is a handful of writes, whereas a daily check that took the lock would have to block that pin or be skipped whenever anything else was publishing — so it would stop being the check an operator can run at any time. The consequence of reading unlocked is that a check can observe a half-applied pair, and the check is fail-closed about it: `rules.ReadPublishedPair` refuses a pair whose list and lock do not describe each other, `--check` reports the refusal on stderr and exits 3, and it never concludes `up-to-date: true` from a pair it could not verify. A transient exit 3 is the correct answer for a check that caught a publication in flight, and Plan 6's timer unit acts on the machine-readable `up-to-date:` line rather than on the exit status.

`--pin-remote` takes the shared control lock **after** the download and conversion have succeeded, so a slow origin never keeps the router's control operations out, and it re-reads the published pair under the lock so a pair that changed or was broken while the download was in flight is refused rather than overwritten.

The two paths, the report format, and the exit codes (`0` success, `2` invalid CLI, `3` state unavailable or publication failed, `4` the control lock is held) are specified in `cmd/mosdns-cdnctl/update_lists.go`, whose default paths are the installed ones so the packaged timer and an operator's pin both act on the list the router reads.

- [ ] **Step 4: Implement the renderer**

Render this behavior:

```text
main:
  if qname matches cn_domains -> goto cn_path
  otherwise                    -> goto foreign_path
cn_path:
  dhcp_forward (generation-scoped domestic cache is internal to this plugin)
  accept
foreign_path:
  foreign_cache
  if has_resp -> accept
  foreign_forward
  accept
```

Render `dhcp_forward` with `cache_entries: 4096`, `upstream_port: 53` and the policy's own `dhcp.failure_policy`; its cache is generation-scoped and therefore cannot return an answer from the previous DHCP DNS set. A published DHCP state carries bare addresses, so the port is a property of this configuration and is written out rather than left to the plugin's default. `Paths.DHCPUpstreamPort` carries it, and an unset (0) value renders as 53 — so a refusal for a port outside 0 and 1..65535 states in its own message that 0 means 53, because by then a reader comparing their value against "between 1 and 65535" has no way to tell 0 from a value that was refused. Later plans insert `cdn_rewrite` around the foreign cache/forward path.

The rendered document is built from typed values and marshalled once, never concatenated out of strings, and the finished bytes are scanned for the known Chinese public resolvers. A `cache.persistent_dump: true` policy is refused rather than rendered as a cache with nowhere to dump to.

Both dispatch rules are the `goto` form and not a `$tag` reference. In MOSDNS v5.3.4 `exec: $cn_path` *calls* the sequence and the parent chain then resumes at its next rule, so a fresh domestic answer would be carried into `foreign_path`, where the cache would store it and later overwrite a fresh answer with it; `goto` abandons the parent chain, which is what makes the absence of a fallback structural rather than a side effect of the `has_resp` guard. Test that with three queries for one China name against a domestic upstream that answers a different address each time: all three answers must be fresh, and the foreign resolver must not see the name.

- [ ] **Step 5: Add default policy and config files**

`configs/policy.yaml` must be byte-for-byte the output of `config.Marshal(config.Defaults())`. `configs/mosdns.yaml` must be byte-for-byte the output of `mosdnsconfig.Render(config.Defaults(), mosdnsconfig.ProductionPaths())`, and must use:

```text
/var/lib/mosdns/lists/cn-domains.txt
/run/mosdns/dhcp-upstreams.json
tcp://127.0.0.1:15353
127.0.0.1:53
```

The China list lives under `/var/lib`, not `/etc`, because the list updater
rewrites it while the router runs and `/etc` stays read-only root-owned
configuration that a package upgrade owns; the renderer refuses a China list or
state document path under `/etc` for the same reason.

The listener entry is the foreign upstream `tcp://127.0.0.1:15353`, never a `udp://` URL, and it has to agree with the `listen_addresses` of `configs/dnscrypt-proxy.toml`. No user-specific DHCP address appears in the file. Both files are generated by the code (`MOSDNS_ROUTER_UPDATE=1 go test ./internal/config ./internal/mosdnsconfig`) and are never hand-edited.

**The China list is a load-bearing start dependency, not a file the service can do without.** `/var/lib/mosdns/lists/cn-domains.txt` is read by `domain_set` at load time, before the router binds anything, and the router has exactly two behaviours for it, with nothing in between. If the file is **missing or unreadable**, `domain_set` fails to initialise, the whole configuration fails to load, and `mosdns-router start` exits non-zero with the loader's error. That is loud, and it is what makes a missing list a visible fault rather than a silent one — but it is a total outage of local DNS, not a degraded mode, so it has to be caught at install. If the file is **present and loads but resolves to no rule at all**, nothing fails: the `qname $cn_domains` condition matches no name, the dispatch falls through to the foreign branch for every query including the China ones, and the domestic branch becomes unreachable while the router reports its queries as answered. The operator's China DNS set is bypassed with no error, no warning, and no mention of the list anywhere in the log — the only symptom is that domestic names now resolve through DNSCrypt from the network the user is leaving. This is the only fail-open state in the design. Nothing this plan's own writers can produce reaches it (`ConvertFS` refuses an entry that resolves to no rules, and `rules.Publish` will not write a list whose digest its lock does not record), but a wiped or truncated `/var/lib` reaches it, and it is the reason the packaging obligation below is stated as it is.

**Packaging obligation.** The installer must provision `/var/lib/mosdns/lists/cn-domains.txt` as part of a successful install, and it must verify the installed bytes against the `list_sha256` in the `source-lock.json` it ships beside them, refusing the install if they disagree. It must never re-pin during install or upgrade: `MOSDNS_ROUTER_UPDATE` is not an install-time input, the committed `configs/source-lock.json` and `configs/cn-domains.txt` are the reviewed pair a fresh installation starts from, and a pin is an explicit operator action through `mosdns-cdnctl update-lists --pin-remote HEAD` under the shared control lock. An install that re-pinned would accept a source nobody reviewed on the strength of the network at that moment, which is exactly the substitution the lock and the archive digest exist to prevent. `update-lists --check` is the mechanism for noticing that the committed source has since moved, and it accepts nothing.

- [ ] **Step 6: Give the policy an effect path**

A policy is inert until something renders it, and with only `mosdns-cdnctl validate`, `status` and `update-lists` there is nothing: an operator who sets `failure_policy: use-last-good` in the installed policy gets a green `validate` and a router still running `disable-current`, because the only copies of the two generated documents are the ones committed to this repository. Implement:

```text
mosdns-cdnctl render --policy PATH --out DIR
```

`render` loads the policy strictly, renders BOTH documents through the renderers the committed files were reviewed under — `mosdnsconfig.Render` for `mosdns.yaml` and `dnscrypt.Render` for `dnscrypt-proxy.toml` — and writes exactly those two files into `--out`. It must never write the China list or the DHCP state, must go through the same safety refusals the renderers already have, and must publish the pair with the same per-file restore obligations `internal/rules` has: a failure that renames one document and cannot rename the other restores the first, and a restore that fails keeps its backup and names it in the error. The document directory and every path the command touches come from an injectable provider defaulting to the production paths, so no test ever writes to `/etc`.

The resolver document is rendered from `dnscrypt.Defaults()`. The policy schema has no stamp field, and this plan does not add one: a custom stamp set is a separate knob, and until it exists the installed `dnscrypt-proxy.toml` is the reviewed Quad9 document (see the File Map).

`validate --policy PATH` keeps its 0/2 contract and never rewrites, but when it is given — or can find — the rendered document directory it prints a machine-readable `rendered-mismatch: <name>` line and a reason for each document that differs from a fresh render, then says plainly that the policy is valid and the installed document is stale. Exit stays 0, because the exit code is about the policy and the policy is valid. A directory with no document in it is a first install, not a stale one, and is not reported.

Cover: default invocation, invalid policy (exit 2), invalid CLI (exit 2), unwritable output directory (exit 3, consistent with the other operational failures in this CLI), both documents written and byte-equal to the reviewed pair, a failure that leaves the previous pair intact, and `validate` reporting a mismatch after a policy edit with no rewrite.

## Plan Acceptance

Run:

```bash
make verify
MOSDNS_REQUIRE_INTEGRATION=1 make test-integration
go test ./internal/config ./cmd/mosdns-cdnctl -v
```

Each of these proves something the others do not, and none of them is a subset of
another:

- **`make verify`** — the whole gate in one run: the exact Go 1.25.8 toolchain
  guard, the Python bridge suite (the state document the Go plugin reads is written
  by Python, so a change to one half the other half's tests cannot see would
  otherwise be a change nobody notices), the unit suites under `-short`, the
  end-to-end suite, the built binaries' build-info read back out of the binary, and
  `go vet`. It also runs `scripts/test-make-entrypoints.sh`, which pins the
  properties the gate itself depends on: that every entry point goes through the
  version guard and stays `-mod=readonly`, that the end-to-end suite is reachable
  from the gate and carries `-count=1`, and that `MOSDNS_REQUIRE_INTEGRATION` is
  exported with a default of 1. A gate that quietly stopped running a suite, or
  stopped insisting, fails here rather than passing green.
- **`MOSDNS_REQUIRE_INTEGRATION=1 make test-integration`** — the end-to-end suite on
  its own, uncached, with the switch that turns "this host cannot run these cases"
  from a skip into a failure. `verify` already reaches it; running it separately is
  what proves it *ran* — on a loopback-only host the switch makes that an error
  rather than a green line with zero coverage behind it. The switch is exported by
  the recipe with a default of 1, so the explicit `1` here is belt and braces for a
  developer who has set `MOSDNS_REQUIRE_INTEGRATION=0` in their environment.
- **`go test ./internal/config ./cmd/mosdns-cdnctl -v`** — the two packages the
  focused command this plan used to name does not reach at all. `internal/config`
  holds the policy encoder that produces `configs/policy.yaml` and the strict
  loader every policy passes through, and `cmd/mosdns-cdnctl` is the command
  surface: `validate`, `status`, `update-lists`, and `render` with its publication
  discipline. The plan's earlier `-run TestRouting` was an unanchored regex that
  selected exactly one top-level case, `TestRoutingSplitSendsEachNameToOnlyItsOwnBranch`,
  and the two packages that turn a policy into an installed configuration were not
  named by any command here at all. The suite grows, so the count is not restated
  here; `go test ./tests/integration -list Test` is how to see what a `-run` would
  select, and a focused run wants an anchored pattern
  (`-run 'TestRoutingSplitSendsEachNameToOnlyItsOwnBranch$'`) rather than a substring
  of a name.

The end-to-end suite is the only place the routing promises are checked: a
document-level test cannot see where a query was sent. It builds the router itself
rather than reading `build/mosdns-router`, so it does not depend on a prior
`make build`, and it skips under `-short`, which is why `go test ./...` on its own
is not in this list.
